# Базовые понятия: AI, LLM, агенты, AI-инженерия, квантование

## 1. AI, ML, LLM: что во что вложено

```
AI (искусственный интеллект)
└── ML (машинное обучение)
    └── Deep learning (нейросети)
        └── Foundation models (большие модели, обученные на огромных данных)
            └── LLM (языковые модели: текст на входе, текст на выходе)
```

- **AI** — общее название для систем, которые решают задачи, требующие «интеллекта»: от шахматной программы на правилах до ChatGPT. Это зонтичный маркетинговый термин, а не технология.
- **ML** — подход, при котором поведение не программируют правилами, а выучивают из данных. Классика: градиентный бустинг для скоринга, рекомендательные системы.
- **Deep learning** — ML на многослойных нейросетях.
- **LLM** — нейросеть-трансформер, обученная предсказывать следующий токен (подробно в [02-how-llm-works.md](02-how-llm-works.md)). Сама по себе LLM — это **функция без состояния**: на вход текст, на выход текст. Она не помнит прошлых вызовов, не ходит в интернет, не читает твою базу и ничего не делает в мире.

## 2. Агент: в чём отличие от LLM

Агент — это **программа вокруг LLM**, которая даёт модели возможность действовать. Формула:

```
Агент = LLM + инструменты + цикл + состояние
```

- **Инструменты (tools)** — функции, которые ты описываешь модели: «найти заказ по id», «выполнить SQL», «отправить письмо». Модель не вызывает их сама, а возвращает JSON вида «хочу вызвать `get_order` с `{"id": 42}`». Вызывает твой код.
- **Цикл** — твой код выполняет инструмент, добавляет результат в историю и снова зовёт модель. Так повторяется, пока модель не скажет «готово».
- **Состояние** — история сообщений, промежуточные результаты, память между шагами.

```python
messages = [user_question]
while True:
    response = llm(messages, tools=tools)
    if response.wants_tool:
        result = run_tool(response.tool_name, response.tool_args)   # это делает ТВОЙ код
        messages += [response, result]
    else:
        return response.text
```

По сути это обычный бэкенд-цикл, в котором ветвление решает не `if`, а модель.

**Workflow против агента.** Есть спектр:
- *Один вызов LLM* — классифицировать обращение, извлечь поля из документа.
- *Workflow* — цепочка вызовов, где порядок шагов задаёшь ты в коде (извлечь → проверить → сформировать ответ).
- *Агент* — порядок шагов и выбор инструментов решает модель.

Чем ближе к агенту, тем гибче система, но тем менее она предсказуема, дороже и сложнее в тестировании. В проде большая часть пользы приходится на один вызов и workflow, а агенты оправданы там, где шаги правда нельзя заранее расписать. Это тема второго этапа курса.

## 3. Что такое AI-инженерия

AI-инженерия — это **построение продуктов поверх готовых моделей**. Модель ты не обучаешь (это ML-инженерия и research), а берёшь как компонент, как берёшь PostgreSQL, и решаешь инженерные задачи вокруг неё.

Главное отличие от обычной разработки: компонент **недетерминирован и иногда ошибается**. Отсюда весь набор задач:

| Задача | Аналог в привычном бэкенде | Этап курса |
|---|---|---|
| Клиент к модели: таймауты, ретраи, логи, учёт токенов | HTTP-клиент к внешнему сервису | 1. Основы LLM |
| Промптинг и structured output (ответ строго по Pydantic-схеме) | Контракт API, валидация | 1. Основы LLM |
| Tool calling, агенты, MCP | Интеграции, оркестрация | 2. Инструменты и агенты |
| RAG: дать модели твои данные через поиск (pgvector) | Поиск, индексы, ETL | 3. RAG |
| Evals: измерить качество на наборе примеров | Тесты, но статистические | 4. Evals и прод |
| Наблюдаемость, стоимость, задержки, безопасность, деплой модели | Мониторинг, SLO, эксплуатация | 4. Evals и прод |

Чего в AI-инженерии обычно нет: обучения моделей с нуля, подбора архитектур, математики оптимизации. Дообучение (fine-tuning) иногда бывает, но это крайняя мера после промптинга и RAG.

Для тебя как тимлида ключевая мысль: 80% этой работы — привычная инженерия (API, схемы, БД, тесты, мониторинг). Новое — это работа с вероятностным компонентом: как формулировать задачу модели, как проверять её ответы и как измерять качество, когда «правильного ответа» в виде `assert` нет.

## 4. Квантование

### Идея

Веса модели обучаются в 16-битных числах с плавающей точкой (BF16/FP16), 2 байта на параметр. Квантование — хранение тех же весов с меньшей точностью: 8, 4, иногда меньше бит. Модель становится в 2–4 раза меньше и быстрее, а качество падает немного.

Почему быстрее: на этапе генерации (decode) скорость упирается в чтение весов из памяти. Вдвое меньше байт — почти вдвое больше токенов в секунду.

### Как это работает: пример

Возьмём блок из 4 весов и сожмём его в 4-битные целые (диапазон от −7 до 7):

```
веса:          [ 0.12,  -0.50,  0.33,  0.90 ]
scale = max(|w|) / 7 = 0.90 / 7 ≈ 0.1286
q = round(w / scale):  [ 1,  -4,  3,  7 ]          ← это и хранится (по 4 бита)
w ≈ q × scale:         [ 0.129, -0.514, 0.386, 0.90 ]   ← восстанавливается при расчёте
```

Хранятся маленькие целые числа плюс один `scale` на блок (блоки обычно по 32–256 весов). Ошибка у каждого веса небольшая, и на миллиардах весов она в основном усредняется. Более умные методы подбирают scale так, чтобы точнее сохранять самые «важные» веса.

### Форматы, которые встретишь

- **GGUF** (Ollama, llama.cpp). Теги вида `Q4_K_M`, `Q5_K_M`, `Q8_0`: цифра — примерное число бит на вес, `K` — схема с вложенными блоками и масштабами, `M` — «средний» вариант по смешению точностей. В Ollama по умолчанию обычно `Q4_K_M`.
- **AWQ, GPTQ** — 4-битные методы для GPU, используются в vLLM.
- **FP8, FP4 (MXFP4, NVFP4)** — квантование в формат с плавающей точкой. Blackwell (твои 5090) аппаратно ускоряет FP8 и FP4. gpt-oss изначально выпущен с весами в MXFP4.

### Компромиссы

| Точность | Размер (от BF16) | Качество |
|---|---|---|
| 8 бит | ~50% | почти без потерь |
| 5–6 бит | ~35–40% | потери малозаметны |
| 4 бита | ~25–30% | небольшие потери, разумный дефолт |
| 3 бита и ниже | ~20% | заметная деградация, особенно на логике и коде |

Практическое правило: большая модель в 4 битах обычно лучше маленькой в 16 битах при том же объёме памяти. Но для точных задач (код, извлечение данных, tool calling) стоит сравнить 4 и 8 бит на своих примерах. Именно этим займёмся в теме evals.

## Вопросы для самопроверки

1. Если LLM не имеет состояния, как тогда ChatGPT «помнит» начало разговора?

<details>
<summary>Ответ</summary>

Историю хранит не модель, а приложение-клиент. При каждом новом сообщении клиент заново отправляет модели **весь диалог**: системный промпт и все прошлые сообщения пользователя и ассистента. «Память» — это просто содержимое контекста в текущем запросе.

Следствия:
- каждый следующий ход дороже предыдущего: входных токенов всё больше;
- длинный диалог упирается в контекстное окно, и тогда старые сообщения обрезают или заменяют их кратким пересказом;
- долгосрочная «память» в продуктах — отдельное хранилище (часто БД), из которого нужные факты подставляются в контекст. По сути это RAG.

</details>
2. Кто физически выполняет SQL-запрос, когда агент «сам сходил в базу»? Какие риски это создаёт и где их контролировать?

<details>
<summary>Ответ</summary>

Выполняет **твой код**. Модель только возвращает JSON с намерением: «вызвать такой-то инструмент с такими аргументами». Выполнять ли его и как, решает приложение.

Риски:
- модель сгенерирует опасный или просто неверный запрос (`DELETE`, `UPDATE` без `WHERE`, тяжёлый `JOIN` по всей базе);
- prompt injection: текст из данных (письмо клиента, поле в БД, документ) уговаривает модель сделать не то, что просил пользователь;
- утечка: модель достанет и покажет данные, которые этому пользователю видеть нельзя.

Контроль — в коде инструментов, а не в промпте:
- не давать модели произвольный SQL, а сделать узкие инструменты с параметрами (`get_order(order_id)`), которые внутри выполняют заранее написанный запрос;
- отдельная роль в PostgreSQL только на чтение и только к нужным таблицам, при необходимости row-level security;
- проверка прав текущего пользователя внутри инструмента;
- `statement_timeout` и `LIMIT`;
- подтверждение человеком для любых изменяющих действий;
- лог всех вызовов инструментов с аргументами.

Общий принцип: относиться к модели как к недоверенному клиенту, так же, как к пользовательскому вводу в API.

</details>
3. Модель на 32B в `Q4_K_M` или модель на 14B в `Q8_0`: какая займёт больше памяти и какую ты бы взял для извлечения полей из договоров? Как бы проверил выбор?

<details>
<summary>Ответ</summary>

**Память.** `Q4_K_M` в среднем около 4,5–5 бит на вес, `Q8_0` около 8,5 бита.
- 32B × ~0,6 байта ≈ 19–20 ГБ;
- 14B × ~1,06 байта ≈ 15 ГБ.

Больше займёт 32B в 4 битах, и сверху ещё нужна память под KV-кэш. На одной 5090 (32 ГБ) помещаются обе.

**Что брать.** По умолчанию 32B в 4 битах: при близком объёме памяти больше параметров обычно дают лучшее понимание текста, а потери от 4-битного квантования невелики. Но это эвристика, а не закон: на конкретной задаче может выиграть и 14B. Зато она будет быстрее.

**Как проверить.** Собрать 30–50 реальных договоров с эталонной разметкой нужных полей. Прогнать обе модели с одинаковым промптом и схемой ответа и посчитать:
- точность по каждому полю;
- долю ответов, которые прошли валидацию схемы;
- скорость и занятую память.

Выбрать по цифрам. Это и есть evals, четвёртый этап курса.

</details>
